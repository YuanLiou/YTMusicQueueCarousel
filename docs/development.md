# 開發指南

本文件說明如何在不偏離 [`spec.md`](./spec.md) 的前提下實作與驗證 MVP。產品行為衝突時，以 `spec.md` 為準。

## 1. 技術原則

MVP 使用原生 JavaScript、CSS 與 Chrome Manifest V3，不使用 React、動畫套件或建置框架。執行時不需要後端服務，也不應加入追蹤、分析或遙測。

動畫以 `transform`、`opacity` 與 `requestAnimationFrame` 為主。CSS transition 適合吸附與狀態切換；`requestAnimationFrame` 只在拖曳或慣性運動期間執行。不要在每一幀讀寫會觸發 layout 的尺寸或位置屬性。

擴充套件應盡量使用 Shadow DOM 隔離 Cover Flow 樣式，避免 YouTube Music 的全域 CSS 汙染覆蓋層，也避免擴充套件樣式外洩到原生播放器。

## 2. 預期責任分界

Manifest 負責宣告 Manifest V3、`music.youtube.com` 的執行範圍、瀏覽器工具列 action、必要權限與內容腳本。權限應保持最小化，不得為方便而要求所有網站、瀏覽紀錄或不必要的網路權限。

背景 service worker 只負責接收瀏覽器工具列 action，找到當前的 YouTube Music 分頁並通知內容腳本切換 Cover Flow。它不保存播放佇列，也不處理動畫。

內容腳本負責辨識 YouTube Music 播放列、注入播放列按鈕、在每次開啟時擷取佇列快照、建立覆蓋層、監聽互動，以及把明確的播放要求交回原生佇列項目。

Chrome isolated content script 無法直接讀取 YouTube Polymer 元件的 `row.data`。需要元件資料時，使用一個最小化的 MAIN world bridge 唯讀擷取 queue row，經序列化 DOM event 傳回 isolated content script。Bridge 不操作播放器、不呼叫網路 API，也不保存資料；isolated 端仍須正規化文字並限制可接受的圖片 host。

資料正規化與索引計算應與 DOM 操作分離，維持成可由 Node 內建測試工具測試的純函式。動畫狀態也應以單一選取索引為基準，避免 DOM 成為唯一狀態來源。

## 3. 已確認的頁面事實與整合策略

2026-08-14 以目前 YouTube Music 播放頁唯讀確認，頁面可辨識「即將播放」佇列、各曲目的播放控制、下方播放器列的上一首／下一首與音量控制。佇列項目可提供歌曲名稱與圖片網址，因此一般歌曲與 Video 的縮圖方案可先從頁面既有資料實作。

YouTube Music 是單頁應用程式。內容腳本不能假設首次載入後 DOM 永遠不變，也不能只在 `DOMContentLoaded` 時注入一次。應以範圍受控的 `MutationObserver` 偵測播放器列被建立或替換，確保 Cover Flow 按鈕存在且不重複注入。

播放器列的 RWD 可能只以 CSS 切換不同控制群，不一定替換整個元件。Cover Flow 按鈕應綁定實際位於 viewport 底部的可見播放器列；桌面版優先放在可見音量控制左側，compact 版則放入可見的 mobile controls。視窗 resize 與播放器列子樹重繪後都必須重新判定 anchor，並移動同一個既有按鈕，避免重複或永久消失。

窄版 `PLAYER_PAGE_OPEN` 狀態會在控制自動隱藏時，直接替底部播放器列寫入 inline `visibility: hidden`。播放器列與按鈕 anchor 的結構判定應以 `display`、實際尺寸及 viewport 位置為準，不得因暫時的 inherited visibility 將仍有 layout 的節點視為不存在。Carousel 開啟期間再由 active class 暫時強制實際底部播放器列保持可見與不透明，確保原生控制及 Carousel 按鈕可操作；Carousel 關閉時移除 active class，完整還原 YouTube Music 的原生顯示行為。

頁面可能同時存在可見項目、隱藏項目、過場副本或尚未載入完成的透明 GIF 圖片。佇列正規化不能只用歌曲名稱去重，因為同名歌曲可能合法重複；也不能把每個匹配節點都視為獨立曲目。應先鎖定實際佇列列元素，再以原生列的穩定識別資訊、播放目標與順序建立快照。

DOM selector 應分層處理。優先使用語意角色、可存取名稱、原生元件責任與彼此相對位置；必要時才使用元件標籤或 class。所有 selector 都應集中管理，避免散落在動畫或事件處理程式中。若必要節點不存在，功能應顯示空狀態或停止注入，不得影響原生播放器。

## 4. 佇列快照與資料模型

每次由關閉狀態切換為開啟狀態時，重新讀取當下已載入的佇列。快照至少包含穩定的列參照或可重新定位資訊、曲目名稱、藝人名稱、圖片候選、佇列順序與是否為目前播放曲目。

覆蓋層開啟期間不因 MutationObserver 發現新增推薦就重建曲目集合。播放器目前曲目仍需獨立監聽；當它改變且新曲目存在於快照中，更新播放索引並把中央封面平滑移至該曲目。

若播放中的曲目不在既有快照中，MVP 應保持快照不變並安全維持目前畫面。不得在覆蓋層開啟期間偷偷加入新曲目。使用者關閉後重新開啟即可取得新快照。

長佇列不必同時建立所有封面 DOM。資料陣列必須保留完整快照，但畫面可以只渲染中央附近的可見窗口，並在索引移動時回收封面節點。這是維持流暢度的主要策略之一。

## 5. 圖片處理

優先從 MAIN world bridge 取得佇列元件提供的最大縮圖候選，再退回 DOM 的 `srcset`、`currentSrc` 或 `src`。2026-08-14 已驗證 `yt3.googleusercontent.com` 與 `lh3.googleusercontent.com` 的 `=w<width>-h<height>` 尺寸參數與元件候選一致；DOM fallback 可以只對這兩個 host 將尺寸提升至至少 544×544，不得改寫其他 host 或未知格式。

封面顯示區固定為正方形。一般專輯封面使用 `object-fit: cover`；Video 的 16:9 縮圖也使用置中 `object-fit: cover` 裁切。圖片載入錯誤時切換至同尺寸 Placeholder，顯示歌曲名稱，不讓破圖圖示進入 Cover Flow。

圖片可直接作為 `<img>` 顯示。MVP 不需要把遠端圖片繪製到 canvas 或轉成 WebGL texture，因此應避免引入跨來源 canvas 汙染與額外解碼負擔。

## 6. 視覺與動畫模型

Cover Flow 舞台使用不透明或接近不透明的黑色背景。中央封面正面顯示，左右封面依相對中央索引計算水平位移、深度、縮放、向外旋轉角度與層級。封面倒影可以使用同一張圖片的鏡像元素與漸層遮罩實作，不需要 canvas。

Shadow host 應提供黑色背景與裁切，底部只延伸至跨出播放器列邊界的透明 seekbar 合成層底緣，不得涵蓋整個播放器控制列。YouTube Music 在窄視窗可能同時保留播放器頁頂端列與 viewport 底部列，版面測量不得直接取 DOM 中第一個播放器列；應從可見候選中選擇底緣最接近 viewport 底部者，再由該列的 seekbar 與播放器列實測矩形計算延伸深度。Carousel 舞台本身仍停在播放器列頂端，避免封面、文字與互動區進入播放器列。原生底部播放器列維持較高 z-index，控制與 seekbar 仍可操作。垂直空間不足時，以 `max-height: 620px` 切換精簡品牌樣式與全封面播放控制；互動語意與播放委派不得改變。

每個畫面更新都由「曲目索引相對於中央索引的距離」推導 transform，不累積增量座標。這能避免快速輸入後浮點誤差、封面錯位與 z-index 不一致。

拖曳期間直接更新連續位置；放開後依位移與速度選擇目標索引，再以單一吸附動畫完成。邊界互動應分開保存未限制的輸入位置、合法選取位置與橡皮筋位移：卡片仍以合法索引計算旋轉、深度與層級，只把整個封面舞台沿水平方向阻尼平移，結束互動後以單一 spring 回到零位移。鍵盤邊界回彈使用更小、較慢的 spring。滾輪事件應合併同一手勢的高頻輸入，並使用較短的結束 debounce，避免大力滾動後停留在橡皮筋頂峰。

橡皮筋最大位移應依響應式封面尺寸縮放，並以桌面尺寸的目標距離為上限。不得只使用固定像素上限，避免視窗縮小後位移相對於封面過大。

`will-change` 只套用在實際可見或正在動畫的封面。不要對整個長佇列永久宣告大量合成層。動畫結束後應清除不再需要的 frame callback 與暫時狀態。

## 7. 輸入與事件邊界

覆蓋層開啟時才攔截方向鍵、`Enter`、`Esc` 與覆蓋層內的 wheel／pointer 操作。文字輸入框或其他可編輯元素取得焦點時，不得劫持鍵盤事件。

側邊封面點擊只更新選取索引。中央封面點擊與 `Enter` 才發出播放要求。Play Button 是中央封面的視覺與可操作控制，必須有可存取名稱，不能只靠 hover 才能被鍵盤使用者發現。

開始拖曳後應設定合理的移動門檻。超過門檻視為拖曳並抑制 click；未超過門檻才視為點擊，避免放開滑鼠時意外播放。

## 8. 原生播放整合

播放所選曲目時，優先操作快照對應的 YouTube Music 原生佇列播放控制。不要自行變更網址來模擬播放，也不要呼叫未公開網路 API。

發出播放動作後，以原生播放器的目前曲目狀態驗證是否成功。若原生列已被單頁應用程式替換，應嘗試以快照中的識別資訊重新定位一次；仍找不到時停止，不得誤點其他曲目。

## 9. 播放列按鈕生命週期

Cover Flow 按鈕放在音量控制左側，視覺尺寸、可點擊區與顏色應融入 YouTube Music 原生播放列，但使用自有圖示，不複製 Apple 或 YouTube 品牌資產。

注入必須具備冪等性。頁面導航、播放器重新渲染或迷你播放器狀態改變後，最多只能存在一個有效按鈕。內容腳本卸載或功能失效時，不得留下持續攔截事件的孤兒節點。

## 10. 空狀態與安全失效

擷取不到任何有效曲目時，覆蓋層顯示「沒有曲目」。若只有部分項目缺少圖片或藝人資訊，仍顯示可辨識曲目，並依規格使用 Placeholder 或省略空的藝人文字。

若 YouTube Music 改版導致無法找到播放器列，瀏覽器工具列 action 不得造成頁面錯誤。若無法取得任何有效曲目，播放列按鈕必須隱藏，工具列 action 不得建立覆蓋層；佇列內容出現後按鈕應自行恢復。任何錯誤都不得中斷原生音訊、影片或播放器控制。

## 11. 測試策略

自動化測試使用 Node 內建測試工具，不引入第三方測試框架。純函式測試至少覆蓋佇列正規化、合法同名歌曲、重複 DOM 副本、透明圖片排除、目前曲目辨識、起點與終點索引、空佇列、Placeholder 資料，以及快速輸入後的索引收斂。

手動 Chrome 驗證至少涵蓋一般專輯佇列、含 Video 縮圖的佇列、沒有可用曲目的頁面、長佇列、曲目自然結束、原生上一首／下一首、兩個 Cover Flow 入口、再次開啟快照更新、所有輸入方式、中央 hover 與播放，以及瀏覽器 console 無未處理錯誤。

動畫驗證應在 Chrome DevTools Performance 中確認拖曳與吸附期間沒有連續 layout thrashing、沒有失控的 frame callback，並以正常硬體加速環境的視覺穩定 60 fps 為目標。無法客觀驗證的情況不得回報為已通過。

## 12. 開發流程

開始實作前先依 [`spec.md`](./spec.md) 提出可驗收的 Definition of Done，取得使用者確認後才修改程式碼。每一階段依「實作、執行 Unit Test、手動驗證、報告」完成。

開發中遇到可重現的頁面陷阱、selector 失效、圖片限制或效能問題時，將事實與重現條件記錄到 [`findings.md`](./findings.md)。使用者明確指定的工作流程應直接更新至 [`rules.md`](./rules.md)；從實作或除錯歸納的 Lessons Learned，則必須有實際證據才能加入。

若實作需要改變 `spec.md` 的產品行為，立即停止相關修改，先說明衝突並取得使用者同意。文件與程式碼的變更都必須經過 diff 檢查；除非使用者另外要求，不自動 commit 或 push。
